Maintain actual implementation evidence; do not mark controls passed from documentation or enabled SDKs. Legal notices must match implemented data flows. Production operator/privacy contact, processors, retention, secure backup/restore and free-tier limits remain unresolved release requirements.

## Mandatory security requirements

The user supplied the controls below before implementation. Repeated items have been consolidated without dropping their intent. All statuses are pending implementation and verification, except the initial environment-file ignore patterns. Do not mark a control satisfied because it is written here.

| ID | Required control | Implementation and evidence needed before release |
| --- | --- | --- |
| S01 | Remove/hide secret API keys from the frontend. Use only a public database identifier or publishable key where needed | Separate public configuration from server secrets. Convex deployment URLs and documented auth publishable keys may be public. Deploy credentials and provider/private API keys must never enter the bundle. Scan source, build output, and browser responses. Hiding a key in frontend code is not protection. |
| S02 | Keep `.env` out of GitHub. Purge Git secrets | Ignore real `.env*` files and key material. Commit only placeholder examples. Scan tracked/staged files and history. If a real credential leaked, revoke or rotate it, then remove exposed content and remediate history through a reviewed plan. No existing commits were found during discovery. |
| S03 | Use a real authentication provider | Managed Google and GitHub OAuth plus email sign-up. Select and configure a supported provider. Verify issuer/audience, expiry, recovery, logout, and account linking. Do not implement a homegrown password system. |
| S04 | Enforce server-side authentication. Never trust browser user IDs | Resolve identity from a verified session/token in each protected server function. Reject unauthenticated and forged-token requests. Client-supplied identity fields cannot authorize an action. |
| S05 | Enable row-level security. Lock record access. Check permissions on the server | In Convex, enforce ownership and permissions in every public function rather than a SQL RLS toggle. Default-deny record reads, updates, deletion, list results, file access, and cross-record relationships. Test user A against user B's records directly. |
| S06 | Block field tampering | Allowlist writable fields. Derive owner and role fields on the server. Reject unexpected fields and unauthorized reassignment, including linking another user's course or semester. |
| S07 | Validate every input on the server | Apply Convex argument and return validators and bounded business rules. Parse and validate HTTP bodies separately. Cover types, lengths, IDs, dates, enums, relationships, page sizes, resource URLs, and extracted timetable data. Test malformed and oversized input. |
| S08 | Stop storing tokens in localStorage. Secure session cookies | No auth/session/refresh tokens in localStorage or other persistent JavaScript storage. Use provider-managed session handling, Secure/SameSite cookie settings appropriate to OAuth, bounded lifetime, revocation, and HttpOnly protection for durable credential cookies. Inspect the actual SDK storage and cookies. If strict HttpOnly session tokens are required, select an architecture that supports them. |
| S09 | Hash passwords | If email/password is selected, the managed provider handles secure password hashing, reset, and verification. Never store plaintext, reversibly encrypted passwords, or password hashes in the app's own course database. Email-code or magic-link flow may avoid app passwords entirely. |
| S10 | Rate-limit logins and add bot protection | Configure auth-provider throttling and bot defenses. Server-verify challenges where applicable. Verify failed-login, sign-up, password-reset, and email-code abuse behavior. Do not rely on a disabled button as enforcement. |
| S11 | Rate-limit every endpoint | Inventory all exposed app queries, mutations, actions, HTTP routes, uploads/downloads, and auth routes. Document and test an enforceable per-identity/origin budget with shared server-side state or a supported gateway/platform control. Cap expensive work and response pagination. Resolve Convex read/subscription limitations explicitly. Mutation-only throttling is not complete coverage. |
| S12 | Add 2FA for admins | Require verified MFA before any privileged app action if admin roles are introduced. Roles come from trusted server/provider data. Require MFA on project/provider administrator accounts where supported. Verify that an ordinary user or an admin without the required second factor cannot perform admin actions. Do not create admin features merely to check this item. |
| S13 | Verify webhook signatures | For every webhook actually introduced, verify the provider signature against the raw body before processing, validate timestamp/replay windows, and make processing idempotent. Reject missing, invalid, expired, or replayed signatures. If no webhooks exist, record that with endpoint-inventory evidence. |
| S14 | Restrict upload types and sizes | Allow only agreed file types. Enforce server-side byte limits, content/MIME checks, bounded PDF page count, extraction time, and file count. Validate original bytes when uploaded and always validate extracted data. Client extension checks are feedback only. Test disguised files, oversized files, malformed PDFs, and exhausted budgets. |
| S15 | Make storage private | No public bucket, directory listing, or permanent public URL for private student files. Tie files to verified owners and authenticate each private download. Convex direct file URLs are bearer-accessible. Use owner-checked HTTP serving or do not retain source PDFs. Test unauthorized byte retrieval. |
| S16 | Lock CORS to the domain | Explicit allowlist for application-owned HTTP endpoints and auth callbacks. No credentialed wildcard. Verify production and approved development origins. CORS is not authorization: direct non-browser calls still require identity and permissions. Document controls available on managed Convex transports. |
| S17 | Add security headers and force HTTPS | Verify deployed CSP, framing restrictions, nosniff, Referrer-Policy, Permissions-Policy, and HSTS where the deployment supports it. Enforce HTTPS and avoid mixed content. GitHub Pages header control is unresolved. Use a suitable proxy or hosting path rather than claiming a meta tag covers every header. |
| S18 | Encrypt sensitive data | Use HTTPS/TLS in transit, verified provider encryption at rest, and encrypted/private backups. Classify collected fields and minimize sensitive data. Decide whether any specific fields need additional application encryption. Do not confuse at-rest encryption with end-to-end encryption. |
| S19 | Avoid raw SQL with user input. Parameterize queries | Use Convex's validated database APIs. No SQL database is currently selected. If SQL is ever introduced, use bound parameters, never string-concatenated user input. Do not translate the checklist into an unnecessary SQL dependency. |
| S20 | Escape user content | Use framework escaping. Sanitize allowlisted rich HTML/Markdown output if introduced. Restrict URL schemes and unsafe links. Test script tags, event attributes, dangerous links, and imported content. Never execute PDF contents or extracted text as instructions or code. |
| S21 | Trim API responses. Hide stack traces | Explicit response shapes and return validators. Do not return entire user/provider records or secret fields. User-facing errors omit stack traces, internal paths, credentials, and sensitive data. Redact server logs and telemetry. Test error and successful response payloads. |
| S22 | Patch vulnerable packages and scan dependencies | Pin the chosen manager and lockfile, audit runtime/build/test dependencies, inspect install scripts before execution, and fix reachable critical/high vulnerabilities before release. Test updates. Do not blindly force dependency upgrades. Record reviewed lower-severity findings and review dates. |
| S23 | Back up the database and test restore | Define backup schedule, retention, encryption, and restricted access. Include file data if retained. Restore to an isolated environment and verify records, relationships, owner isolation, and file access. Provider backups alone are not evidence that this project's restore procedure works. |
| S24 | Verify before finalizing | Keep a control-to-evidence record for S01-S23. Run focused negative security tests, actual browser session/storage checks, dependency/secret scans, deployed-header/origin checks, and the restore drill. Record provider-configuration tasks separately from code checks. Unresolved applicable controls block release. |


## Release evidence

Maintain S01–S24 evidence covering two-user isolation, forged identity, field/relationship tampering, malformed inputs, session inspection, endpoint budgets, private bytes, file/quota races, hostile content, secret/dependency scans, deployed headers/origins and restore. Applicable unresolved controls block release. SQL RLS/public key/bucket instructions must be translated to Convex's actual ownership/storage APIs, not implemented through an unnecessary second database.

No cloud endpoints or account sessions are currently configured. Browser checks and dependency scans for the preview do not establish production compliance. Use project-specific security review and hardening skills. Follow Phases.md for delivery order and record what actually ran in Memory.md.
